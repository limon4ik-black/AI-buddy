# Встроенная база знаний

`knowledge/v1/` содержит 23 исходных JSON с готовыми embeddings (637 чанков,
Qwen/Qwen3-Embedding-0.6B, 1024 измерения). Это данные приложения, они включаются
в Git и Docker-образ. `junk/` больше не используется для штатного импорта.

`manifest.json` фиксирует имя набора, версию, модель, размерность, видимость
`company`, имя каждого JSON, его SHA-256, ID документа и количество чанков.
Этот набор содержит общую базу знаний, доступную всем пользователям RAG.
Личные заметки и данные с командными ACL сюда не добавляются.

После получения репозитория на другом ноутбуке:

```sh
make rag         # запуск приложения, миграции и импорт автоматически
# либо только БД и импорт, без модели и LLM:
make rag-import
```

Команды выполняются из корня репозитория. Они требуют настроенного Docker;
`make configure` подготавливает локальные секреты. Импорт не использует Groq API.
Изменения передаются на другие ноутбуки после обычного commit/push и git pull;
файлы volume PostgreSQL в Git не переносятся.

## Обновление набора

Сохраняйте выпущенные версии. Для следующего снимка скопируйте JSON в
`knowledge/v2/`, добавьте новые или изменённые JSON и удалите отсутствующие.
Из каталога `rag-service` пересоздайте манифест и проверьте данные:

```sh
.venv/bin/python -m src.knowledge manifest data/knowledge/v2 --version v2
.venv/bin/python -m src.knowledge validate data/knowledge/v2
```

В релизе измените `DEFAULT_DIRECTORY` в `src/knowledge.py` на новую папку,
чтобы следующий `make rag` / `make rag-import` автоматически выбрал её.
Для ручного импорта другого набора из уже собранного образа:

```sh
docker compose --env-file .env -f deploy/compose.yaml --profile rag run --rm --no-deps rag \
  python -m src.knowledge import /app/data/knowledge/v2
```

Не меняйте `dataset_name` при обновлении того же набора: по нему импорт удаляет
устаревшие документы. Удаление файлов из снимка допустимо, пустой набор отклоняется
для защиты от случайного удаления всей базы. Откат к предыдущему снимку выполняется
той же командой импорта с его папкой; при следующем старте сервис снова выбирает
`DEFAULT_DIRECTORY` (или переменную процесса `RAG_KNOWLEDGE_DIR`).

Весь набор проверяется до записи: контрольные суммы, модель, размерность,
ненулевые конечные векторы, уникальность ID и индексов чанков. Изменённые документы
заменяются вместе со всеми чанками одной транзакцией; неизменённые пропускаются.
Коллизия с документом Note Service или другого набора откатывает весь импорт.
В `knowledge_imports` хранится применённая версия и контрольная сумма манифеста.

Миграции `postgresql/migrations/*.sql` применяются и на новой, и на существующей
БД. Уже применённые SQL-файлы изменять нельзя: добавляйте следующий файл.
Старый импорт из `junk/import.py` распознаётся по пустому `embedding_version`:
документы текущего набора принимаются под управление `bundled_json`, прочие
сохраняются как `legacy_json` и не становятся общедоступными автоматически.

## Интеграционные тесты

Запускайте на отдельной PostgreSQL с pgvector, не на рабочей БД:

```sh
RAG_TEST_DATABASE_URL=postgresql://user:password@localhost:5432/test_db \
  .venv/bin/python -m pytest -q
```

БД должна быть тестовой и разрешать создание расширения и временных схем.
Без этой переменной тесты БД пропускаются; остальные тесты работают без Docker.
