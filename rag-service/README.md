# RAG Service

Запуск из корня: `make rag`. Нужен `GROQ_API_KEY` в корневом `.env`; модель генерации задаётся `GROQ_MODEL`.

Note Service → Qwen3-Embedding-0.6B → PostgreSQL/pgvector → Groq. Embeddings имеют размерность1024. При наличии CUDA используется GPU/FP16, иначе CPU/FP32. Модель скачивается при первом запуске и сохраняется в volume.

При каждом старте сервис применяет миграции схемы, импортирует встроенный набор JSON,
затем загружает полный снимок документов Note Service. Синхронизация удаляет только
отсутствующие документы источника `note_service`, сохраняя `bundled_json`.
Неизменённые документы повторно не кодируются. Пока процесс работает,
автоматического обновления индекса нет: после изменения документов перезапустите rag.

Основной контракт: POST `/internal/v1/generate`, заголовок `X-Service-Token` со значением RAG_SERVICE_TOKEN. Тело: `{requestId, userId, message, history, userContext}`. userId — Auth users.id / JWT sub, обязан совпадать с userContext.profile.userId. UUID владельца из БД чата сюда не передаётся. Несовпадение отклоняется с422 до retrieval. В userContext обязательны profile.userId и allowedDocumentIds. До генерации поиск по Note ограничивается разрешёнными ID; встроенный набор с видимостью `company` доступен всем авторизованным пользователям. Ответ: `{answer, sources: [{documentId,title,section}], suggestedAction, mode: "rag"}`.

Старый POST `/chat` с Bearer FRIEND_TOKEN сохранён для совместимости тестов и внутренних клиентов; в общем приложении пользовательские запросы идут только через `/internal/v1/generate`. Не публикуйте сервис напрямую наружу.

GET `/healthz` доступен после загрузки модели и синхронизации индекса. На CPU первый старт может занимать несколько минут.

В `/internal/v1/generate` ответ формируется за два обращения к Groq. Сначала модель
по вопросу и истории возвращает JSON `{"functions": []}` с выбором `get_notes`,
`get_checkpoints`, обеих функций или пустого списка. План проверяется по строгой
схеме: неизвестные функции, аргументы и дополнительные поля отклоняются с общей
ошибкой 502. Пользовательские ID и URL модель не задаёт.

`get_notes` читает `/api/v1/notes` Note Service с исходным JWT пользователя.
`get_checkpoints` берёт задачи и сводку прогресса из авторитетного `onboarding`,
полученного для текущего запроса из Note Service с проверкой Auth ID и JWT.
Выбранные функции выполняются параллельно, каждая максимум один раз. Второй запрос
к модели содержит выбранные данные в JSON и разрешённые фрагменты базы знаний.
Чеклист не передаётся модели автоматически, если функция не выбрана.

Каждая функция передаёт до 20 записей, до 4000 символов на текстовое поле и до
16000 символов текста суммарно; `truncated=true` отмечает неполные данные.
Заметки идут от недавно изменённых к старым. Ошибка функции обозначается
`status=unavailable`, пустая успешная выборка — `status=ok, items=[]`.
Модель получает указание различать эти случаи и сообщать об ограничениях.
Функции поддерживают только чтение. Сервисный `/chat` без пользовательского JWT
сохраняет прежнюю генерацию по базе знаний и не вызывает личные функции.

Для `/internal/v1/generate` также нужен исходный пользовательский JWT в `Authorization: Bearer ...`. До поиска RAG вызывает Info `GET /internal/v1/users/{userId}/context` с тем же JWT и CHAT_SERVICE_TOKEN. Контекст и ACL из Info авторитетны; переданный клиентом контекст не расширяет доступ. Публичный userId всегда равен Auth ID, а не UUID владельца из БД чата.
