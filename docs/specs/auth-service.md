# Auth Service: вход через Google и по коду из письма

Статус: реализованы Google-вход, вход/регистрация по одноразовому коду и восстановление пароля. Сессии — механизм команды: refresh-токен в PostgreSQL (`refresh_sessions`), httpOnly-cookie, access-JWT (EdDSA, 15 минут) на `role=intern`. Формат — REST/JSON. Миграции: `auth/001`–`auth/005` применяются сервисом при старте.

## Схема входа

Пароль сам сессию не открывает. Верные кредиты лишь отправляют на почту одноразовый 6-значный код; сессию открывает ввод кода. Google-вход выдаёт сессию сразу — Google подтверждает почту за нас.

## Ручки

Все пути через публичный гейтвей. Публичные: `register`, `login`, `confirm`, `refresh`, `logout`, `google/*`, `password/*`. Остальные — с `Authorization: Bearer <accessToken>`.

| Метод | Путь | Доступ | Результат |
| --- | --- | --- | --- |
| POST | `/api/v1/auth/register` | публично | Заявка на регистрацию + код на почту (201) |
| POST | `/api/v1/auth/login` | публично | Код на почту (200) |
| POST | `/api/v1/auth/confirm` | публично | Сессия: `accessToken`, `expiresIn`, `user` |
| POST | `/api/v1/auth/password/reset` | публично | Код для смены пароля, если аккаунт есть (200 всегда) |
| POST | `/api/v1/auth/password/confirm` | публично | Смена пароля + новая сессия |
| POST | `/api/v1/auth/refresh` | публично | Ротация refresh, новый access |
| POST | `/api/v1/auth/logout` | публично | Закрытие текущей сессии (204) |
| GET | `/api/v1/auth/me` | JWT | `id`, `email`, `role` |
| GET | `/api/v1/auth/google/login` | публично | Редирект на Google |
| GET | `/api/v1/auth/google/callback` | публично | Сессия + 302 на `APP_ORIGIN` |

## Регистрация: аккаунт только после кода

Регистрация **не создаёт аккаунт**. Пароль (bcrypt) и email кладутся в `pending_registrations` — заявку, а на почту уходит код. Аккаунт появляется в `users` только после ввода кода, и вместе с ним открывается сессия. Заранее созданных на чужую почту «пустых» аккаунтов нет: без кода из чужого ящика заявка ни во что не превращается.

- Повторная регистрация на занятую почту — 409 `email_taken`; на неподтверждённую — заявка обновляется, код улетает заново.
- Логин по email с незавершённой заявкой работает как логин: пароль сверяется с заявкой, после кода заявка превращается в аккаунт.
- Google-вход по подтверждённой почте подчищает заявку на неё.

## Свойства кода

Код живёт 7 минут, одноразовый (сгорает первым правильным подтверждением), привязан к окну запроса через HttpOnly-куку `buddy_login_sid` (10 минут): из чужого браузера код не примется — 400 `no_pending_login` или `invalid_code`. Хэш кода хранится как `sha256(код|sid)`, в открытом виде код не пишется нигде. Активный код на пользователя всегда один: новый запрос затирает старый. Назначение кода (`login` / `reset`) — колонка `purpose` в `login_confirmations`; код логина нельзя потратить на смену пароля и наоборот.

Письмо уходит асинхронно (потолок 45 секунд), поэтому ручки отвечают мгновенно даже при медленном SMTP. Ответ: брендированный HTML (стиль фронта) + текстовый fallback.

## Восстановление и смена пароля

`POST /auth/password/reset` принимает email и отвечает одинаково независимо от того, существует ли аккаунт — по ней нельзя перебирать чужие почты. Код получают только владельцы реального аккаунта.

`POST /auth/password/confirm` (тело: `code`, `newPassword` 10–72 байт) атомарно: сжигает код, обновляет `password_hash`, отзывает **все** refresh-сессии аккаунта, кроме сессии запросившего (если запрос из залогиненного кабинета — текущая сессия выживает), и открывает новую сессию. Ответ тот же, что у `confirm`.

В кабинете смена пароля — тот же сценарий: «Безопасность: сменить пароль» в профиле шлёт код на почту аккаунта и применяет новый пароль.

## Google

Стандартный Authorization Code flow. Юзер ищется по `google_sub`; при первом входе создаётся аккаунт без пароля. К существующей почте подвязывается только если Google вернул `email_verified`, иначе 409 `email_unverified`. Обычные Gmail-аккаунты всегда verified — 409 касается редких Workspace-конфигураций.

## Ограничения и открытые вопросы

1. Access-JWT stateless: после смены пароля чужие access-токены живут до конца своих 15 минут (без рефреша их никто не продлит). Мгновенный отзыв потребовал бы `sid` в JWT и проверки сессии на каждый запрос — обсуждается.
2. `role` захардкожен как `intern` в подписи и проверке JWT (`security/jwt.go`) — расширяется только кодом.
3. Rate-limit стоит на register/login/confirm/password-ручках по IP; лимиты на почту сами по себе не ограничивают частоту одного адреса.
4. Протухшие строки `refresh_sessions` не вычищаются автоматически — запросы их игнорируют, но копятся.

## Настройка

`.env` (см. `.env.example`): `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URL` (должен посимвольно совпадать с Authorized redirect URIs в Google Console), SMTP: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD` (пароль приложения), `SMTP_FROM`. Без `SMTP_HOST` письма пишутся в лог сервиса auth.
