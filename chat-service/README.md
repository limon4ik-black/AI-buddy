# chat-service

MVP-сервис чатов AI Buddy на Go 1.25: REST, одно WebSocket-соединение для всех чатов пользователя, PostgreSQL и HTTP-интеграция с `LLM-service`.

## Запуск

Нужны Go 1.25 и PostgreSQL (проверено на PostgreSQL 18; SQL совместим с PostgreSQL 17).
Из корня репозитория:

```bash
# Только локальная база для разработки. Учётные данные не предназначены для production.
docker run --rm --name buddy-chat-db \
  -e POSTGRES_USER=buddy -e POSTGRES_PASSWORD=local-only -e POSTGRES_DB=chat \
  -p 127.0.0.1:5432:5432 -d postgres:17-alpine

cd chat-service
cp .env.example .env
# В .env установить FRIEND_TOKEN, совпадающий с токеном LLM-service,
# и AI_SERVICE_URL — базовый URL сервиса без /chat.
set -a
. ./.env
set +a
go run ./cmd/chat-service
```

`.env` автоматически не загружается: переменные передаются окружением процесса.
При запуске сервис проверяет соединение с БД и атомарно применяет встроенную
идемпотентную миграцию `migrations/001_init.sql`. Нужны права создания таблиц и
индексов в выделенной базе/схеме. Используются только таблицы `chats` и `messages`.
Ошибка подключения или миграции останавливает запуск. Отмена миграции откатывает
транзакцию. Для удаления схемы в локальной базе сначала удалить `messages`, затем
`chats`; автоматического отката с удалением данных нет.

```bash
go build -o /tmp/chat-service ./cmd/chat-service
# Либо из каталога chat-service:
docker build -t buddy-chat-service .
docker run --rm --env-file .env -p 127.0.0.1:8080:8080 buddy-chat-service
```

В Docker задайте адреса БД и AI, доступные из контейнера (localhost относится к
самому контейнеру). PostgreSQL и AI запускаются отдельно.

| Переменная | Значение / назначение |
| --- | --- |
| `DATABASE_URL` | Обязательно: PostgreSQL DSN |
| `AI_SERVICE_URL` | Обязательно: базовый HTTP(S) URL AI |
| `FRIEND_TOKEN` | Обязательно: секрет для `Authorization: Bearer` |
| `HTTP_ADDR` | `:8080` |
| `AI_HTTP_TIMEOUT` | `60s`: полный таймаут HTTP-запроса к AI |
| `REQUEST_TIMEOUT` | `75s`: REST-операция или обработка одного WS-сообщения |
| `WS_ORIGINS` | Разрешённые дополнительные host[:port] браузерных Origin через запятую; по умолчанию только host запроса |

`SIGINT`/`SIGTERM` отменяют активные операции, закрывают WebSocket и дают HTTP и
WS-обработчикам до 10 секунд на завершение, затем закрывается пул PostgreSQL.

## API

Каждый запрос, включая WebSocket handshake, требует `X-User-ID: <uuid>`.
Отсутствующий или некорректный заголовок даёт `401`. Gateway обязан проверять JWT,
перезаписывать заголовок и закрывать прямой внешний доступ к этому сервису.
В браузере заголовок добавляется gateway при проксировании WS handshake.
Идентификатор пользователя из тела запроса не используется.

| Endpoint | Результат |
| --- | --- |
| `POST /chats` | `201`: `{id,title,created_at}`, название «Новый чат» |
| `GET /chats` | `200`: `[{id,title,updated_at}]`, `updated_at DESC` |
| `GET /chats/{id}/messages` | `200`: `[{id,role,content,created_at}]`, от старых к новым по `id` |
| `DELETE /chats/{id}` | `204`: чат и сообщения удалены |
| `GET /ws` | WebSocket upgrade, один канал для всех чатов пользователя |

Пустые списки возвращаются как `[]`. Неизвестный и чужой чат одинаково дают `404`;
некорректный UUID чата — `400`. Ошибки REST: `{"message":"..."}`. Сбой БД даёт `503`
без внутренних подробностей.

```bash
curl -X POST http://localhost:8080/chats \
  -H 'X-User-ID: 11111111-1111-4111-8111-111111111111'
curl http://localhost:8080/chats \
  -H 'X-User-ID: 11111111-1111-4111-8111-111111111111'
```

Клиент WebSocket отправляет текстовый JSON:

```json
{"chat_id":"<uuid>","content":"Как устроен процесс разработки?"}
```

Успешный ответ и ошибка:

```json
{"type":"message","chat_id":"<uuid>","role":"assistant","content":"Процесс разработки..."}
```
```json
{"type":"error","chat_id":"<uuid>","message":"Не удалось получить ответ AI"}
```

Некорректные JSON, UUID, чужой чат и пустое сообщение возвращают `type: error`;
соединение остаётся пригодным для следующих сообщений. Лимит WS-фрейма — 64 KiB.
Текст обрезается по краям и должен содержать 1–8000 Unicode-символов, согласно
контракту AI. Неизвестные поля WS-сообщения отклоняются.

## Интеграция и ограничения MVP

Контракт проверен по `../LLM-service/src/main.py`: `POST /chat` принимает
`{message,history}`, возвращает `{answer,sources}`. Сохраняется `answer`, `sources`
не используются. Текущий `message` не дублируется в истории. Из-за ограничения
`ChatRequest.history` AI получает последние 20 предшествующих сохранённых
сообщений текущего чата в исходном порядке. REST возвращает всю историю.

Сообщение пользователя сохраняется до обращения к AI. При таймауте, ошибке HTTP
или некорректном ответе оно остаётся в БД; сообщение assistant сохраняется только
после успешного ответа. Каждое сохранение сообщения атомарно обновляет
`updated_at`, в том числе при последующей ошибке AI. Если сохранение ответа в БД
не удалось, клиент получает ошибку, а успешный ответ ему не отправляется.
Повторная отправка считается новым сообщением.

Обработка последовательная в пределах одного WS-соединения. Читатель сокета
работает отдельно для обнаружения отключения во время AI-запроса; генерации
в нём нет. Между несколькими соединениями одного пользователя порядок генераций
не сериализуется. Для MVP клиенту следует держать одно соединение и ждать ответа
на отправленное сообщение. Полная история REST не имеет пагинации.

Реальный AI требует собственной конфигурации и запущенного `LLM-service`;
автотесты используют HTTP-заглушку его проверенного контракта.

## Структура

```text
cmd/chat-service/main.go     конфигурация, запуск, graceful shutdown
internal/chat/              модели, интерфейсы, сценарий отправки сообщения
internal/store/             PostgreSQL, проверка владельца, транзакции
internal/ai/                HTTP-клиент существующего AI API
internal/transport/         REST, X-User-ID, WebSocket, публичные ошибки
internal/testutil/          репозиторий в памяти для тестов
migrations/                встроенная SQL-миграция
.env.example               переменные без секретов
Dockerfile                 сборка Go 1.25
```

## Проверка

```bash
go test -race -timeout 60s ./...
go vet ./...
go build ./...

# PostgreSQL-тест создаёт изолированную временную схему и удаляет её.
# Нужны права CREATE SCHEMA в указанной тестовой базе.
CHAT_TEST_DATABASE_URL='postgres://buddy:local-only@localhost:5432/chat?sslmode=disable' \
  go test -race -timeout 60s ./...
```

Без `CHAT_TEST_DATABASE_URL` PostgreSQL-тест явно пропускается. Проверяются REST и
изоляция пользователей, WS для нескольких чатов, ошибки валидации и AI,
сохранность пользовательского сообщения при ошибке AI, лимит и порядок истории,
отмена HTTP-запроса при отключении WS, миграция, сортировка и каскадное удаление.
